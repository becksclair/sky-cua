# Plan: Codex Desktop Compatibility and Linux Backend Parity

## Current Summary

`sky-cua` now implements the main portability layer needed to behave like Codex Desktop's bundled Computer Use plugin while staying usable from MCP-first hosts such as OpenCode and Pi.

The implementation keeps the runtime boundary in `sky-cua-client mcp` and the shared plugin resources, while the Codex Desktop compatibility work is deliberately narrow:

- Build and install a `computer-use` compatibility plugin from `sky-cua`.
- Keep the upstream `chrome` and `browser-use` bundled plugins available beside `computer-use`.
- Patch Codex Desktop only at the plugin-availability seam so Browser Use and Chrome appear in Settings when `computerUse` is enabled on Linux.
- Keep OpenCode/Pi compatibility through `.mcp.json`, skills, and local MCP server registration rather than Codex-only prompts.

  - `doctor`
  - `setup_accessibility`
  - `setup_window_targeting`
  - `list_apps`
  - `list_windows`
  - `focused_window`
  - `activate_window`
  - `get_app_state`
  - `perform_action`
  - semantic and physical action tools
- `crates/sky-cua-platform/src/model.rs` contains the shared contracts:
  - `DoctorReport`, `DoctorReadiness`, `BrowserIntegrationReport`
  - `DoctorSessionEnvReport`, `DoctorSessionEnvRepair`
  - `WindowInfo`, `WindowTarget`, `TerminalWindowInfo`
  - `ActionName::PerformAction`
  - `AppStateSnapshot.doctor_report`
- `crates/sky-cua-service/src/element_resolver.rs` resolves action targets by `element_index`, `element_identifier`, or semantic selector data from the cached snapshot.
- `crates/sky-cua-linux/src/backend.rs` wires the action surface into AT-SPI, physical input, window targeting, doctor/setup, and fallback snapshot paths.

### Windowing Backends

The Linux backend now has a unified windowing module:

- `crates/sky-cua-linux/src/windowing/registry.rs`
- `crates/sky-cua-linux/src/windowing/types.rs`
- `crates/sky-cua-linux/src/windowing/target.rs`

- `crates/sky-cua-linux/src/windowing/gnome_extension.rs`

- `crates/sky-cua-linux/src/windowing/hyprland.rs`
- `crates/sky-cua-linux/src/windowing/i3.rs`

Supported backends now include KWin, X11, GNOME Shell Introspect, the bundled GNOME Shell extension, COSMIC helper, Hyprland, and i3. Terminal metadata enrichment is implemented from `/proc` and feeds `WindowTarget` selectors such as `tty`, `terminal_pid`, `terminal_command`, and `terminal_cwd`.

### Workspace Metadata

The KWin and X11 `workspace: None` gap is closed:

- `crates/sky-cua-linux/src/kwin.rs` parses workspace/desktop values from KWin window metadata.
- `crates/sky-cua-linux/src/x11/windowing.rs` queries and parses `_NET_WM_DESKTOP`.
- `crates/sky-cua-linux/src/windowing/registry.rs` passes KWin and X11 workspace values through to `LinuxWindowInfo`.
- `WindowInfo.workspace` remains backend-native metadata only; it is not a targeting/filter field.

### Doctor and Setup

Doctor/setup is no longer missing:

- `doctor` returns structured platform, portal, accessibility, windowing, input, and browser integration reports.
- `setup_accessibility` reports before/after doctor state and skips unnecessary work when the accessibility tree is already ready.
- `setup_window_targeting` installs/enables the GNOME Shell extension path and includes `permissions_hint` when window listing still fails.
- Linux doctor includes `at_spi_enabled`, `ydotool_socket`, browser checks, native-host manifest checks, and windowing notes.
- `get_app_state` includes `doctor_report` and can surface readiness alongside ordinary snapshot diagnostics.

Remaining doctor risk is live-environment breadth, not missing core shape. The high-value future hardening is to keep improving hydrated session-bus recovery and desktop-specific blocker wording as more real launch environments are observed.

### Chrome, Browser Use, and Codex Desktop

Implemented pieces:

- `crates/sky-cua-chrome-host/` provides the Linux native messaging host.
- `resources/chrome-extension/codex/1.1.4_0/` contains the extracted upstream Codex Chrome extension fallback payload.
- `scripts/build_plugin.py` stages upstream OpenAI bundled resources from `SKY_CUA_UPSTREAM_CODEX_RESOURCES`, `SKY_CUA_OPENAI_BUNDLED_RESOURCE_ROOT`, or the sibling `codex-desktop-linux` resource path.
- `scripts/build_plugin.py` copies upstream `chrome` and `browser-use` plugins when available, removes macOS sidecars, ensures marketplace entries for `chrome`, `browser-use`, and `computer-use`, and installs `sky-cua-chrome-host` as `resources/plugins/openai-bundled/plugins/chrome/extension-host/linux/<arch>/extension-host`.
- `resources/chrome_preflight.py` syncs `chrome`, `browser-use`, and the `computer-use` compatibility plugin into the Codex bundled marketplace cache.
- `resources/chrome_preflight.py` writes exact Chrome/Brave/Chromium native-host manifests for `com.openai.codexextension`.
- `resources/chrome_preflight.py` enables `chrome@openai-bundled` and `browser-use@openai-bundled` in `config.toml`; it stages the compatibility `computer-use@openai-bundled` entry disabled so it does not collide with the active `sky-cua` server.
- `scripts/install_plugin.py` runs browser preflight on Linux after installing the bundle.
- `bin/sky-cua-browser-preflight` is included as the plugin-local wrapper.

Codex Desktop side patching is intentionally small and lives in `/home/bex/projects/sky/CodexDesktop-Rebuild`:

- `scripts/patch-computer-use.ts` widens Linux `computerUse` feature availability.
- The same patch strips external Browser Use build-flavor gates.
- It also lets Browser Use and Chrome companion descriptors remain available when `computerUse` is enabled, preventing the early partial-feature snapshot from pruning them before the full browser flags arrive.
- The companion matcher is bounded to known Browser Use/Chrome descriptor identities and to the destructured `features` alias, so unrelated descriptors that happen to use browser feature flags fail loud instead of being patched.

## Current Recommendation

Use the current approach:

- Rename/present the Codex-compatible plugin as `computer-use`.
- Keep Browser Use and Chrome as upstream `openai-bundled` companion plugins.
- Keep Codex Desktop patching limited to Linux feature availability and companion descriptor availability.
- Keep OpenCode/Pi compatibility through `.mcp.json`, bundled skills, and MCP server semantics.

This is the least invasive path that matches Codex Desktop's bundled-plugin expectations while avoiding a Codex-only fork of the actual `sky-cua` runtime.
